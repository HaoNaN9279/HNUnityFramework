```
Editor/EditorUI/                                   ← Editor 侧
    HNSmartInspector.cs           ★ 主入口：[CustomEditor(typeof(MonoBehaviour), editorForChildClasses: true)]
    HNSmartInspectorStyles.cs     样式常量
    Descriptors/                   ★ 扩展接口体系
        IPropertyDescriptor.cs    字段级属性描述器接口
        IClassDescriptor.cs       类级属性处理器接口
        DescriptorRegistry.cs     注册中心（项目扩展点）

    Utility/

        EditorLayout.cs           布局辅助
```

**设计要点：**

- **HNSmartInspector** 以 `[CustomEditor(typeof(MonoBehaviour), editorForChildClasses: true)]` 全局注册，自动覆盖所有无专属 Editor 的 MonoBehaviour。组件有自定义 Editor 时不受影响。发现目标类型有框架自定义属性时走增强绘制路径，否则 `DrawDefaultInspector()` 快速返回
- **运行时属性**放在 `Runtime/HN.Framework.Unity` 层，继承 `PropertyAttribute`，用户脚本只需 `using` 命名空间即可使用，不依赖 Editor 程序集
- 大部分属性继承 `PropertyAttribute`，其 `PropertyDrawer` 在 Unity 默认 Inspector 中也独立生效
- **类型缓存 + 反射缓存**避免每帧反射开销

**属性系统（全量 19 个属性全部已实现 ✅）：**

| 类别 | 属性 | Phase 1 | 说明 |
|------|------|:-------:|------|
| 交互 | `[ReadOnly]` | ✅ | 灰色显示，不可编辑 |
| 动作 | `[Button]` | ✅ | 在 Inspector 底部渲染为方法按钮 |
| 可见性 | `[ShowIf]` / `[HideIf]` | ✅ | 条件显示/隐藏控制 |
| 装饰 | `[Title]` | ✅ | 字段前渲染标题（含可选副标题） |
| 装饰 | `[InfoBox]` | ✅ | 字段前渲染信息/警告/错误框 |
| 装饰 | `[PropertyOrder]` | ✅ | 控制字段绘制顺序 |
| 可见性 | `[ShowInInspector]`, `[HideInInspector]` | ✅ | 强制显示/隐藏非序列化字段 |
| 交互 | `[EnableIf]`, `[DisableIf]` | ✅ | 条件启用/禁用 |
| 验证 | `[Required]` | ✅ | 字段空值 / Null 高亮红色 |
| 验证 | `[ValidateInput]` | ✅ | 自定义校验回调 |
| 布局 | `[FoldoutGroup]` | ✅ | 同组字段折叠面板 |
| 布局 | `[BoxGroup]` | ✅ | 同组字段框线面板 |
| 布局 | `[TabGroup]`, `[HorizontalGroup]`, `[VerticalGroup]` | ✅ | 高级布局 |
| 动作 | `[OnValueChanged]` | ✅ | 值变化回调 |

**扩展机制：**

- `IPropertyDescriptor` — 字段级属性描述器接口，在 `PropertyField` 前后插入自定义绘制逻辑
- `IClassDescriptor` — 类级属性处理器接口（如 FoldoutGroup 的开合状态管理），带 `Order` 排序控制
- `DescriptorRegistry` — 注册中心，项目在 `[InitializeOnLoad]` 中调用注册方法添加自定义属性处理器
- 扩展路径：实现接口 → 注册到 Registry → 自动参与 HNSmartInspector 绘制链，无需修改框架代码

**依赖**：UnityEditor 内建 API + System.Reflection。无新增外部依赖。

### E9 — 资源质检与自动化构建

- **状态**：📋 规划中
- **命名空间**：`HN.Framework.Editor.BuildPipeline`

**核心设计**：

规则框架以注册中心模式组织。框架定义检查规则接口，项目按资源 Importer 类型注册自定义规则，可扩展到任意自定义 AssetImporter：

```
Rules/                          # 规则框架
├── IAssetRule                  # 规则接口（开放供项目实现）
├── AssetRuleRegistry           # 按 ImporterType 分组的注册中心
├── RuleResult                  # 检查结果数据模型
└── Presets/                    # 框架预设通用规则
    ├── MissingScriptRule       # 缺失脚本检测
    ├── NamingConventionRule    # 命名规范
    ├── ReferenceIntegrityRule  # 引用完整性检查
    └── AddressablesRule        # Addressables 配置检查

Validator/                      # 校验执行
├── AssetValidator              # 校验调度器
└── AssetValidatorWindow        # 校验结果窗口（EditorWindow）

Pipeline/                       # 构建管线
├── IBuildStep                  # 步骤接口
├── BuildPipelineOrchestrator   # 多平台打包编排
├── BuildPipelineWindow         # 构建控制窗口
└── Steps/                      # 内置步骤
    ├── PreBuildValidationStep  # 质检门禁
    ├── AddressablesBuildStep
    ├── PlayerBuildStep
    └── PostBuildStep

Redundancy/                     # 冗余资源检测
├── DependencyGraph             # 资源引用图
├── RedundancyScanner           # 冗余扫描器
└── RedundancyCleanerWindow     # 可视化清理窗口

Versioning/                     # 版本管理
├── VersionConfig               # 版本配置（ScriptableObject）
├── VersionManager              # 版本号 + Git tag 管理
└── BuildManifest               # 构建清单生成

Reporting/                      # 构建报告
├── BuildReportGenerator        # 报告生成器（JSON/Markdown）
└── BuildReportWindow           # 报告查看窗口

Settings/                       # 配置集成
├── BuildPipelineSettings       # 全局设置
└── BuildPipelineSettingsProvider
```

**规则扩展方式**：

- 框架定义 `IAssetRule` 接口，包含 `TargetImporterType` 类型标识和 `Validate(assetPath)` 方法
- `AssetRuleRegistry` 按 AssetImporter 子类类型分组管理规则，维护 ImporterType → 规则列表映射
- 项目在 `[InitializeOnLoad]` 中调用注册方法添加自定义规则，可针对标准 Importer（TextureImporter/ModelImporter 等）或自定义 Importer
- `AssetValidator` 遍历资源目录时自动识别资源的 Importer 类型，匹配并执行对应规则集
- 项目扩展点明确：实现接口 → 注册到 Registry → 自动参与校验，无需修改框架代码

**框架预设通用规则**：

| 规则 | 检查内容 |
|------|----------|
| MissingScriptRule | Prefab/Scene 中 MonoBehaviour 引用断裂 |
| NamingConventionRule | 文件名是否符合命名正则需要 |
| ReferenceIntegrityRule | 资源引用链完整性（贴图/材质/Prefab 引用目标是否存在） |
| AddressablesRule | Addressables 同 Key 冲突、必填 Label 缺失、Bundle 命名冲突 |

**预设规则定位**：以上规则在任何项目中都具有约束力，不绑定特定项目业务逻辑。非通用规则（如纹理最大尺寸、压缩格式、模型动画类型、音频加载方式等）由项目通过注册中心自定义注册，框架不做预设。

**依赖**：UnityEditor 内建 API，无新增外部依赖。无需运行时程序集变更。

## 附录B：关键设计决策记录

### B.1 ReferencePool 和 HNLogicTime 为何保留静态？

| 类 | 保留静态的理由 |
|----|---------------|
| `ReferencePool` | 线程安全的零 GC 工具类，不持有任何业务状态。类比 .NET 的 `ArrayPool<T>.Shared`。所有操作无副作用，无需生命周期管理。 |
| `HNLogicTime` | 纯数据类，仅提供 Time/DeltaTime/LogicFrameCount 三个静态属性。不依赖任何外部服务，也不被任何模块管理。 |

### B.2 ObjectPool 为何拆分在 Core/Unity 两侧？

`ObjectPoolManager` 通过 `PoolBase` 抽象接口管理所有池。Unity 侧的 `GameObjectPool` 实现 PoolBase，由 GameWorldDriver 创建并通过 `RegisterPool` 注册到 PoolManager。因此 PoolManager 不需引用 UnityEngine，可留在 Core 程序集中。

### B.3 FishNet 集成策略

Core 层（`noEngineReferences: true`）无法引用 FishNet，只定义 `INetworkManager` 接口。Unity 层的 `FishNetNetworkManager` 实现该接口，同时最大程度复用 FishNet 内置能力（NetworkBehaviour/SyncVar/RPC/Spawn/Interest Management），不自建同步协议。

### B.4 SRP 为何可选且无依赖？

不同项目（甚至同一项目的不同平台）可能需要不同的渲染管线（Built-in/URP/HDRP）。强制 SRP 会阻止框架在其他管线下的使用。所有系统必须在启动时检测管线类型并自动适配。

### B.5 为何选择 MemoryPack 而非继续使用手写 JSON？

MemoryPack 在 C# 中是目前最快的二进制序列化库之一，其性能远超 JSON（通常 5-10x 更快，零 GC 分配）。对于网络消息序列化（高频小消息）和存档系统（大体积数据），二进制格式的带宽和存储优势显著。

### B.6 为何选择 miniaudio 而非 Unity Audio？

miniaudio 提供跨平台的 C 语言音频引擎，允许框架实现 Wwise-like 的音频功能（Bank 系统、RTPC 参数、状态切换等）。Unity 内置 Audio 系统功能有限且扩展性差，无法满足复杂项目需求。

### B.7 为何选择 Unity GraphView 而非自研图渲染？

GraphView 是 Unity 内置的图编辑框架（Shader Graph、VFX Graph 均基于此）。自研图渲染系统需要大量精力处理节点拖拽、连线、缩放等交互，而 GraphView 已提供完善的 API。

### B.8 为何选择 LitMotion 而非 DOTween？

LitMotion 专为 Unity 设计：**零 GC 分配**（基于 `struct` + `IMotionBuilder` 模式）、**Burst 兼容**（动画计算可运行于 Burst Job）、**更现代的 API**（链式调用 + 取消令牌）、**与 UI 系统深度集成**。

### B.9 为何选择五层动画架构？

此架构源自 Unreal Engine 的 Gameplay Ability System 和动画蓝图设计。五层分离带来：
1. **知识池**：数据收集与决策解耦
2. **决策层**：输入 → 请求的清晰转换
3. **请求层**：优先级仲裁 + 双缓冲避免帧间冲突
4. **行为层**：使用 HFSM 描述动画行为
5. **运动层**：纯物理计算，与动画数据无关

### B.10 UNITY_SERVER 宏策略

| 适用范围 | 做法 |
|----------|------|
| `HN.Framework.Core` 程序集 | **禁止使用** — 保证客户端/服务端代码完全一致 |
| `HN.Framework.Unity` 渲染相关代码 | `#if !UNITY_SERVER` 包裹 |
| `HN.Framework.Editor` | Editor only，天然不进入构建 |

### B.11 IAssetManager 接口统一

原始设计中分为 `IAssetManager`（Core）和 `IAssetOperator`（Unity）两个接口。`IAssetManager` 定义面向业务的高级 API，`IAssetOperator` 定义底层加载原语。`AssetManager`（Unity）同时实现两者，委托底层实现给注入的 Operator。

### B.12 Debug 系统自研理由

不引入第三方调试框架的原因：
1. **框架级集成**：需要与 DebugHub 架构深度绑定
2. **零依赖原则**：第三方调试工具是可选的，不作为必须依赖
3. **结构化日志**：需要 `LogEntry` 携带 `object Context` 实现结构化日志
4. **运行时控制台**：需要终端风格命令输入 + 自动补全，无现成 UGUI 方案
