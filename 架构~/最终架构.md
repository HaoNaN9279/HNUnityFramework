# HNUnityFramework 最终架构

> 生成日期：2026-07-06（更新：整合架构缺口模块）
> 目标平台：Unity 2022.3+，.NET Standard 2.1
> 架构模型：三层架构（DriverLayer → CapabilityModule → Level）+ 菱形多仓库解耦

---

## 一、框架定位与设计哲学

### 1.1 定位

HNUnityFramework 是一个轻量级、模块化的 Unity 游戏开发框架。它不追求"大而全"，而是提供一套可跨项目复用的基础设施，同时保留充分的游戏特定定制空间。

### 1.2 核心设计原则

| 原则 | 说明 |
|------|------|
| **三层架构** | DriverLayer（驱动）→ CapabilityModule（通用能力）→ Level（关卡逻辑+视图），层间依赖单向 |
| **消除静态单例** | 有状态的 Manager 全部由 GameWorld 持有实例，仅工具类（ReferencePool、HNLogicTime）保留静态 |
| **纯 C# 核心** | `HN.Framework.Core` 设置 `noEngineReferences: true`，编译期强制零 Unity 依赖 |
| **Addressables 优先** | 运行时资源加载唯一路径；ResourcesOperator 保留但标记 `[Obsolete]` |
| **模块化能力系统** | Capability 层定义接口于 Core，实现于 Unity，Editor 提供调试面板 |
| **跨仓库菱形依赖** | 四个仓库单向依赖，下层不感知上层 |

### 1.3 程序集三层拆分

```
┌──────────────────────────────────────────────┐
│         HN.Framework.Editor                  │  Editor only
│         编辑器工具 + 调试面板                   │
│         references: Core + Unity (via GUID)   │
└────────────────────┬─────────────────────────┘
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
┌──────────────────┐  ┌──────────────────────────────┐
│ HN.Framework     │  │     HN.Framework.Unity       │
│  .Core           │  │                              │
│  (noEngineRefs   │  │  平台适配 · Unity 实现        │
│   = true)        │  │  UnityEngine · Addressables   │
│                  │  │  FishNet（封装）               │
│  纯 C# 逻辑层     │  │                              │
│  接口 · 抽象 ·   │◄─┤  references: Core             │
```

## 二、多仓库菱形依赖架构

### 2.1 四仓库拓扑

```
                       ┌─────────────────┐
                       │   策划设计内容    │  ← 最上层
                       │   (Design Repo)  │
                       │  零代码，纯装配   │
                       │  Prefab / 场景 / UI 组装 │
                       └───────┬─┬───────┘
                               │ │
                    ┌──────────┘ └──────────┐
                    │                       │
                    ▼                       ▼
        ┌──────────────────┐    ┌──────────────────┐
        │   项目脚本         │    │   纯美术资源       │
        │  (Scripts Repo)   │    │   (Art Repo)      │
        │  程序维护          │    │  美术维护          │
        │  游戏玩法逻辑       │    │  零代码，按实体组织 │
        │  视图层代码         │    │  模型/贴图/材质/动画│
        │  Editor 工具       │    │  Shader/RenderPipeline│
        └────────┬─────────┘    └────────┬──────────┘
                 │                       │
                 └───────────┬───────────┘
                             │
                             ▼
                ┌────────────────────────┐
                │   HNUnityFramework      │  ← 最底层（本仓库）
                │   (Framework Repo)      │
                │                        │
                │  HN.Framework.Core     │  ← 纯 C# 逻辑层
                │  HN.Framework.Unity    │  ← Unity 平台层
                │  HN.Framework.Editor   │  ← 编辑器工具层
                └────────────────────────┘
```

### 2.2 仓库职责与边界

| 仓库 | 内容 | 维护团队 | 包含代码？ | 依赖 |
|------|------|----------|:----------:|------|
| **Framework** | 框架自身：DriverLayer + CapabilityModule 接口 + Level 基础设施 | 框架开发 | ✅ | Unity + Addressables |
| **Art** | 按实体分类的美术资产（模型/贴图/材质/动画）；项目 Shader 文件 + 渲染管线配置 | 美术 | ❌ | Framework（Shader 依赖） |
| **Scripts** | 游戏玩法逻辑 + 视图层代码 + Editor 工具 | 程序 | ✅ | Framework（asmdef 引用） |
| **Design** | 引用美术资源的 Prefab、游戏逻辑场景、UI 组装 | 策划 | ❌ | Art + Scripts（Unity GUID 引用） |

### 2.3 三大基石技术

| 领域 | 技术 | 说明 |
|------|------|------|
| 资源管理 | **Addressables** | 替代 Resources；`ResourcesOperator` 保留但标记 deprecated |
| 配置表 | **Luban** | Excel → C# 代码生成 + 运行时数据加载；框架 Sheet 编辑器负责 Unity 内资源引用编辑 |
| 网络 | **FishNet** | 通过 `HN.Framework.Unity` 封装传输层；`HN.Framework.Core` 只定义 `INetworkManager` 接口 |

### 2.4 解耦原则

```
程序写代码时 ──→ 不需要美术资源，不需要策划 Prefab，只需 Framework
美术做资源时 ──→ 不需要程序代码，不需要策划场景，只需 Framework（Shader 依赖）
策划搭场景时 ──→ 不需要修改代码，不需要修改源美术资产，引用 Art + Scripts 装配
```

**核心规则：**
- **单向依赖**：上层依赖下层，下层绝不依赖上层
- **Design 是装配层**：零代码，只有 `.prefab` / `.unity` / `.asset`
- **Art 是纯资源**：不含 Prefab、不含代码，按实体分目录（不按资产类型分）
- **Scripts 是纯代码**：包含 LogicModule（玩法逻辑）和 ViewModule（视图代码）

### 2.5 架构层 → 仓库映射

| 架构层 | 归属仓库 |
|-----------|----------|
| **Level.ViewModule**（视图代码：ViewFactory 等） | Scripts |
| **Level.ViewModule**（3D 场景、Pawn、UI 的 Prefab 装配） | Design |
| **Level.LogicModule**（任务/战斗/商城等玩法逻辑） | Scripts |
| **CapabilityModule**（接口定义 + 平台实现） | Framework + Scripts（游戏特定实现） |
| **DriverLayer**（GameWorld + 基础类库 + 平台抽象） | Framework |
| **Editor 工具** | Framework + Scripts |

| 依赖方向 | 方式 | 说明 |

## 五、GameWorld 驱动模型

### 5.1 静态单例消除

所有有状态的 Manager 从静态单例迁移为 GameWorld 持有的实例：

| 类 | 旧模式 | 新模式 |
|----|--------|--------|
| `ControllerManager` | `static ControllerManager Instance` | `world.ControllerManager`（实例） |
| `ObjectPoolManager` | `static ObjectPoolManager Instance` | `world.PoolManager`（实例） |
| `ProcedureManager` | `static ProcedureManager Instance` | `world.ProcedureManager`（实例） |
| `ReferencePool` | `static` 全部静态 | **保持不变** — 线程安全工具类 |
| `HNLogicTime` | `static` 全部静态 | **保持不变** — 纯数据类 |

### 5.2 GameWorld 双组件模式

```
                 HN.Framework.Core（纯 C#）            HN.Framework.Unity（Unity 层）
                 ────────────────────────            ──────────────────────────────

                 ┌──────────────────────┐           ┌──────────────────────────┐
                 │     GameWorld        │◄──────────│    GameWorldDriver        │
                 │                      │  持有并驱动 │   (MonoBehaviour)         │
                 │  内置模块:            │           │                          │
                 │  · PoolManager       │           │  Awake() → new GameWorld │
                 │  · ProcedureManager  │           │          → 注入平台实现   │
                 │  · ControllerManager │           │          → World.Initialize│
                 │  · DebugHub          │           │                          │
                 │                      │           │  Update() → World.Tick() │
                 │  注入服务:            │←─────────│  LateUpdate() → LateTick │
                 │  · LogProvider       │  注入      │                          │
                 │  · AssetManager      │           │  OnRegisterGameModules() │
                 │  · NetworkManager    │           │    → 虚方法，Scripts 重写 │
                 │  · StorageProvider   │           └──────────────────────────┘
                 │  · LocaleProvider    │            ▲
                 │  · AudioManager      │            │ 继承
                 │  · CutsceneManager   │  ┌─────────┴───────────┐
                 │  · UIManager         │  │     GameEntry        │ ← Scripts 仓库
                 └──────────────────────┘  │  (Scripts Repo)      │
                                          │                      │
                                          │  OnRegisterGameModules│
                                          │    → 注册游戏特定模块 │
                                          └──────────────────────┘
```

### 5.3 Tick 循环顺序

```
Tick():
  PoolManager.Tick()       → 池回收调度
  ProcedureManager.Tick()   → 流程状态 Tick
  ControllerManager.Tick()  → 所有 Controller + ControllerUnit
  AssetManager?.Tick()      → 资源自动卸载 + 预加载消费

LateTick():
  PoolManager.LateTick()
  ProcedureManager.LateTick()
  ControllerManager.LateTick()
  AssetManager?.LateTick()
```

### 5.4 Scripts 仓库 GameEntry 示例

```csharp
// 继承 Framework 的 GameWorldDriver，重写 OnRegisterGameModules
public class GameEntry : GameWorldDriver
{
    protected override void OnRegisterGameModules(GameWorld world)
    {
        // 注册游戏特定的 Controller
        world.ControllerManager.RegisterController(new BattleController(world));

        // 注入游戏特定的服务实现
        world.NetworkManager = new GameNetworkService();
        world.StorageProvider = new GameStorageService();
    }
}
```

#### C6.1 状态同步机制

- **状态**：📋 规划中

**基于 FishNet SyncVar + SyncList，不自建同步协议。**

```
SyncVar — 简单字段自动同步：
  NetworkEntityView 中声明 [SyncVar] 字段
  → FishNet 仅同步变更字段（delta compression）
  → SyncVar 变更回调 → 驱动 View 更新

SyncList / SyncDictionary — 集合增量同步：
  [SyncObject] SyncList<ItemSlot> Inventory
  → 仅发送 add/remove/update 操作（非全量）
  → 客户端自动维护镜像集合

SyncVar → IReadOnlyModel 绑定：
  Model（Core）     ← 服务端权威计算
  NetworkEntityView  ← SyncVar 同步到客户端
  IReadOnlyModel     ← View 通过 PropertyBinder(V3) 监听
```

**帧同步（可选，需 HNFixedPoint D2.5）：**
```
- 锁定逻辑帧率，客户端输入通过 ServerRpc 发送
- 服务端收集所有输入 → 确定性 Tick(HNFixedPoint)
- 校验和比对检测不同步
```

#### C6.2 客户端预测与服务器校验

- **状态**：📋 规划中

**使用 FishNet 内置 Prediction 系统，不自建。**

```
FishNet Prediction API：
  - PredictionManager：管理预测状态快照
  - Reconciliation：服务端矫正 → 客户端回滚 + 重放未确认操作
  - LagCompensation：服务端回溯到客户端过去时刻做 Hit 检测
```

## 十一、动画系统五层架构

### 11.1 分层概览

```
┌────────────────────────────────────────────────────────────────┐
│                    Unity Playable Graph                        │
│                         ▲                                      │
│  Layer 5: 运动层 (Motion Layer)                                │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 物理计算 · 根运动集成 · 碰撞解决 · 地面吸附 · IK 求解     │  │
│  └──────────────────────────────────────────────────────────┘  │
│                         ▲                                      │
│  Layer 4: 行为层 (Behavior Layer)                               │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 动画处理 · 混合树评估 · 状态机转换 · 运动数据生成         │  │
│  └──────────────────────────────────────────────────────────┘  │
│                         ▲                                      │
│  Layer 3: 请求层 (Request Layer)                                │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 请求过滤 · 优先级仲裁 · 双缓冲交换                         │  │
│  └──────────────────────────────────────────────────────────┘  │
│                         ▲                                      │
│  Layer 2: 决策层 (Decision Layer)                               │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 移动输入 · 战斗输入 · 上下文判断 · AnimationRequest 生成   │  │
│  └──────────────────────────────────────────────────────────┘  │
│                         ▲                                      │
│  Layer 1: 世界信息收集 (Knowledge Pool / Sensor)                │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 玩家位置 · 敌人位置 · 地形 · 武器状态 · 速度 · 输入状态   │  │
│  └──────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

### 11.2 Layer 1 — 世界信息收集（Knowledge Pool）

收集全局状态（速度、武器、地形等），每帧在 Decision Layer 之前更新。

### 11.3 Layer 2 — 决策层（Decision Layer）

基于 Knowledge + 输入生成 `AnimationRequest`（LocomotionRequest、CombatRequest 等）。

### 11.4 Layer 3 — 请求层（Request Layer）

双缓冲机制（Buffer A/B 交换）+ 优先级仲裁（击倒 > 受击 > 攻击 > 闪避 > 移动 > 待机），过滤非法请求。

### 11.5 Layer 4 — 行为层（Behavior Layer）

动画状态机转换（内部使用 L2 HFSM）、混合树评估（1D/2D），生成 `MotionData`。

### 11.6 Layer 5 — 运动层（Motion Layer）

根运动集成 → 碰撞解决（CapsuleCast）→ 地面吸附 → IK 求解（Foot/LookAt/Hand）→ Playable Graph 输出。

### 11.7 数据流

```
KnowledgePool → DecisionLayer → AnimationRequest
  → RequestLayer (filter + prioritize) → BehaviorLayer (state machine + blend)
  → MotionLayer (physics + IK) → PlayableGraph → Unity Animator
```

### 13.1 状态

| `ShaderLibrary/Shadows.hlsl` | 阴影采样 |
| `ShaderLibrary/PostProcess.hlsl` | 后处理函数 |

### 13.3 无依赖约束

**核心约束**：所有其他框架系统必须**无条件**在 SRP 未启用时正常工作。SRP 是可选的渲染优化选择，不是依赖。

启动时自动检测管道类型（Built-in / URP / HDRP / Custom），动态适配渲染路径。不得有以下行为：
- `#if` 包围核心逻辑使其依赖 SRP
- SRP 未启用时出现编译错误
- 功能降级仅因 SRP 未启用

### 13.4 Shader Library 使用方式

框架提供的 `.hlsl` 包含文件是便利工具，非依赖。Art 仓库的 Shader 可选择性 `#include` 这些文件以复用通用操作（PBR 照明、阴影采样、后处理）。

### 13.5 未来规划

在 Unity SRP API 上实现完整自定义渲染管线，包括：
- Forward+ 渲染路径
- 级联阴影贴图
- 延迟渲染支持
- GPU Driven 管线

## 附录B：关键设计决策记录

### B.1 ReferencePool 和 HNLogicTime 为何保留静态？

| 类 | 保留静态的理由 |
|----|---------------|
| `ReferencePool` | 线程安全的零 GC 工具类，不持有任何业务状态。类比 .NET 的 `ArrayPool<T>.Shared`。所有操作无副作用，无需生命周期管理。 |
| `HNLogicTime` | 纯数据类，仅提供 Time/DeltaTime/LogicFrameCount 三个静态属性。不依赖任何外部服务，也不被任何模块管理。 |

### B.2 ObjectPool 为何拆分在 Core/Unity 两侧？

`ObjectPoolManager` 通过 `PoolBase` 抽象接口管理所有池。Unity 侧的 `GameObjectPool` 实现 PoolBase，由 GameWorldDriver 创建并通过 `RegisterPool` 注册到 PoolManager。因此 PoolManager 不需引用 UnityEngine，可留在 Core 程序集中。

### B.3 FishNet 集成策略

Core 层（`noEngineReferences: true`）无法引用 FishNet，只定义 `INetworkManager` 接口。Unity 层的 `FishNetNetworkManager` 实现该接口，同时最大程度复用 FishNet 内置能力（NetworkBehaviour/SyncVar/RPC/Spawn/Interest Management），不自建同步协议。预置的 MonoBehaviour 组件（NetworkTransform、NetworkAnimator 等）由框架自行封装以保持架构一致性。

### B.4 SRP 为何可选且无依赖？

不同项目（甚至同一项目的不同平台）可能需要不同的渲染管线（Built-in/URP/HDRP）。强制 SRP 会阻止框架在其他管线下的使用。所有系统必须在启动时检测管线类型并自动适配。

### B.5 为何选择 MemoryPack 而非继续使用手写 JSON？

MemoryPack 在 C# 中是目前最快的二进制序列化库之一，其性能远超 JSON（通常 5-10x 更快，零 GC 分配）。对于网络消息序列化（高频小消息）和存档系统（大体积数据），二进制格式的带宽和存储优势显著。

### B.6 为何选择 miniaudio 而非 Unity Audio？

miniaudio 提供跨平台的 C 语言音频引擎，允许框架实现 Wwise-like 的音频功能（Bank 系统、RTPC 参数、状态切换等）。Unity 内置 Audio 系统功能有限且扩展性差，无法满足复杂项目需求。

### B.7 为何选择 Unity GraphView 而非自研图渲染？

GraphView 是 Unity 内置的图编辑框架（Shader Graph、VFX Graph 均基于此）。自研图渲染系统需要大量精力处理节点拖拽、连线、缩放等交互，而 GraphView 已提供完善的 API。复用可大幅降低开发成本，同时保持与 Unity 编辑器一致的操作体验。

### B.8 为何选择 LitMotion 而非 DOTween？

LitMotion 专为 Unity 设计，具有以下优势：
- **零 GC 分配**：基于 `struct` + `IMotionBuilder` 模式
- **Burst 兼容**：动画计算可运行于 Burst Job
- **更现代的 API**：链式调用 + 取消令牌
- **与 UI 系统深度集成**：作为 C13 UI 动画的默认引擎

### B.9 为何选择五层动画架构？

此架构源自 Unreal Engine 的 Gameplay Ability System 和动画蓝图设计，已在大量 3A 游戏中验证。五层分离带来：
1. **知识池**：数据收集与决策解耦，传感器可独立扩展
2. **决策层**：输入 → 请求的清晰转换，易测试
3. **请求层**：优先级仲裁 + 双缓冲避免帧间冲突
4. **行为层**：使用 HFSM 描述动画行为，与游戏逻辑 HFSM 可互操作
5. **运动层**：纯物理计算，与动画数据无关

### B.10 UNITY_SERVER 宏策略

| 适用范围 | 做法 |
|----------|------|
| `HN.Framework.Core` 程序集 | **禁止使用** — 保证客户端/服务端代码完全一致 |
| `HN.Framework.Unity` 渲染相关代码 | `#if !UNITY_SERVER` 包裹（Headless 服务端无需渲染） |
| `HN.Framework.Editor` | Editor only，天然不进入构建 |

### B.11 IAssetManager 接口统一

原始设计中分为 `IAssetManager`（Core）和 `IAssetOperator`（Unity）两个接口。`IAssetManager` 定义面向业务的高级 API（场景组管理、引用计数、进度查询），`IAssetOperator` 定义底层加载原语（同步/异步加载、释放）。`AssetManager`（Unity）同时实现两者，委托底层实现给注入的 Operator。

### B.12 Debug 系统自研理由

不引入第三方调试框架的原因：
1. **框架级集成**：需要与 DebugHub 架构（通道 + 命令 + 模块注册）深度绑定
2. **零依赖原则**：第三方调试工具（如 Odin Inspector 是可选的，不作为必须依赖）
3. **结构化日志**：需要 `LogEntry` 携带 `object Context` 实现结构化日志，Unity 内置 Debug 不支持
4. **运行时控制台**：需要终端风格命令输入 + 自动补全，无现成 UGUI 方案
